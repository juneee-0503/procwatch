# 报警

报警的流程是:

```text
数据 → 判定 → 状态 → 决策 → 通知
```

设计原则只有一句话:**宁可晚报,不可误报。** 报警疲劳比漏报更快摧毁信任,延时确认、迟滞和分组都为此服务。

## 生命周期

每条报警都有状态:

```text
正常 → 观察中 → 触发 → 已确认 → 已恢复 → 正常
```

| 状态 | 含义 |
|---|---|
| 观察中 | 值已异常,但持续时间不够。过滤毛刺的关键 |
| 触发 | 异常持续够久,灯亮、响铃、发通知 |
| 已确认 | 有人看过了,灯不再闪,声音停止,不再提醒 |
| 已恢复 | 值回到恢复阈值之内,并持续够久 |

**只有状态变化才产生事件。** 一条持续一小时的报警只产生几个事件,不是几千个。

## 规则

在设置界面(`,`)编辑,或写在 `modules.conf`:

```text
alert = cpu.usage > 90 clear 80 for 30s clearfor 60s priority high
alert = disk.queue_depth{device=sda} >= 32 priority medium
```

| 部分 | 默认 | 含义 |
|---|---|---|
| 比较 | 必填 | `>` `>=` `<` `<=` |
| `clear V` | 阈值的 10% 以内 | 恢复阈值,必须比触发更宽松,这就是迟滞 |
| `for Ns` | 15s | 持续多久才触发 |
| `clearfor Ns` | 30s | 恢复后持续多久才算恢复 |
| `priority` | medium | `high`、`medium`、`low` |

可用的指标用 `procwatch --dictionary` 查看。

内置规则(可在设置中关闭):

| 规则 | 优先级 |
|---|---|
| CPU 使用率 > 90%,持续 60 秒 | 中 |
| 内存 > 90%,持续 60 秒 | 中 |
| 内存 > 97%,持续 30 秒 | 高 |
| 磁盘 > 90%,持续 60 秒 | 中 |
| 磁盘 > 97%,持续 30 秒 | 高 |
| 每秒新建 TCP 连接 > 500,持续 30 秒(Linux) | 中 |
| procwatch 自身 CPU > 25%,持续 60 秒 | 低 |

攻击发现直接进入“触发”,不经过观察。严重和高级发现会一直保持到有人确认;中级 30 分钟、低级 10 分钟后自动结束。

所有持续时长都用单调时钟,改系统时间不会触发或恢复任何报警。

## 决策:该不该打扰人

| 机制 | 行为 |
|---|---|
| 不重复 | 同一问题持续存在时只提醒:高级 5 分钟一次,中级 30 分钟一次,低级不提醒 |
| 合并 | 10 秒内同一台机器的多条报警,第一条立即发,其余合并成一条 |
| 压制 | 模块信号丢失时,不再报它名下的指标 |
| 维护 | 按时间窗口暂停,到期自动恢复 |
| 确认 | 确认后不再提醒 |

## 三级优先级

灯和声音按迈瑞监护仪的 ISO 模式(出厂默认)设计,数值来自迈瑞操作手册(ePM 10M/12M、T1);手册没写的时序取 IEC 60601-1-8 允许的范围,手册声明报警音符合该标准。

| 优先级 | 灯 | 声音 | 重复间隔 | 消息 | 对外通知 |
|---|---|---|---|---|---|
| 高 | 红色,2 Hz 快闪 | 三响 + 两响 + 三响 + 两响,共 10 响 | 10 秒 | `***`,红底白字 | 是 |
| 中 | 黄色,0.625 Hz 慢闪 | 三响 | 20 秒 | `**`,黄底黑字 | 是 |
| 低 | 青色,常亮 | 单响 | 20 秒 | `*`,青底黑字 | 否 |

| 声音参数 | 值 | 来源 |
|---|---|---|
| 基频 | 600 Hz | ePM 手册 A.8 |
| 三级节奏 | 见上表 | ePM、T1 手册 |
| 重复间隔 | 10、20、20 秒 | T1 手册默认值 |
| 暂停时长 | 2 分钟 | T1 手册默认值 |
| 高级脉冲和间隔 | 脉冲 150 ms,x = 100 ms,3 与 2 之间 2x+t = 350 ms,两组之间 400 ms | IEC 范围内的取值 |
| 中级 | 脉冲 200 ms,间隔 200 ms | IEC 范围内的取值 |
| 低级 | 脉冲 250 ms | IEC 范围内的取值 |
| 上升时间 | 脉冲的 10% | IEC |
| 谐波 | 600、1200、1800、2400 Hz,相差不超过 15 dB | IEC |

这些参数由 `src/common/sound.rs` 的测试从生成的波形里实际测量。

**这不是迈瑞的录音。** 手册只公开了上面这些参数,没有公开脉冲的具体毫秒数和音色,实际听感取决于监护仪的扬声器,没有和真机对比过。同一品牌不同型号也有差别:例如 T1 的低级灯是黄色,这里按 ePM 用青色。

迈瑞的 Mode 1、Mode 2 没有实现,手册只描述了听感,没有给出频率。

## 报警灯

右上角的矩形就是报警灯,旁边显示报警内容。终端高度不足 20 行或宽度不足 70 列时,灯会隐藏,报警仍在 `#` 列表里。

| 按键 | 功能 |
|---|---|
| `!` | 确认全部 |
| `@` | 暂停声音,默认 120 秒,灯继续闪 |
| `#` | 报警列表,`Enter` 确认单条 |

灯上的 `♪off` 表示声音已关闭。

声音用系统播放器:macOS 的 `afplay`,Linux 的 `paplay`、`pw-play` 或 `aplay`,Windows 的 PowerShell。都没有时用终端响铃。

## 可靠性

**报警事件不会丢。** 采样数据走有界的事件总线,压力大时可以丢;报警走独立的通道,队列不限长。这个通道是安全的,因为引擎只在状态变化时才说话,而状态很少。

**报警不拖累采集。** 判定在自己的线程,通知在另一个线程。webhook 卡住不影响判定,判定也不影响采集。

**监护仪自己也被监护。** 下面这些指标都可用于规则和 Prometheus:

| 指标 | 含义 |
|---|---|
| `alarm.firing` | 当前触发数 |
| `alarm.notify_failed` | 通知失败数 |
| `alarm.eval_ms` | 评估耗时 |
| `kernel.bus_dropped` | 总线丢弃数 |

## 通知去向

不配置也能用:灯、声音照常工作,每条报警都写入数据目录的 `alarms.jsonl`。

要发到别处,在设置(`F2`)的 Notifications 里选 Add a destination,输入一行:

| 写法 | 含义 |
|---|---|
| `webhook URL dingtalk min high` | 格式可以是 `json`、`slack`、`dingtalk`、`feishu`、`wecom` |
| `syslog min medium` | 系统日志 |
| `file /var/log/alarms.jsonl` | 文件 |
| `command /usr/local/bin/page-oncall` | 运行命令,不经过 shell |

`min` 默认 `high`。保存后立即生效,选 Send a test alarm 试发一条。详见[服务器防御](defense.md#报警)。

## 手动触发

检查灯、声音和通知是否正常,不用等真的出问题:

```bash
scripts/trigger-alarm.sh high
```

Windows 上用 `.\scripts\trigger-alarm.ps1 high`。

| 参数 | 效果 |
|---|---|
| `high`、`medium`、`low` | 触发一条 |
| `all` | 三级各一条 |
| `sequence` | 低、中、高依次触发,间隔 5 秒 |
| `storm [N]` | 同时触发 N 条中级报警,默认 20,用来看合并和限流 |
| `clear` | 结束全部测试报警 |

需要 procwatch 正在运行,已过 STANDBY,加载了 `alarm` 模块,并且和脚本是同一个用户。没有会话接收时,脚本会报错而不是悄悄结束。更新代码后要先 `cargo build`,再重启 procwatch:重新构建不会改变已经在运行的会话。

测试报警走真实链路:响铃、亮灯、写记录、发通知。标题固定以 `[TEST]` 开头,所以配置了目的地时对方也会收到,看得出是测试。

高优先级报警不会自己结束。确认后灯不再闪,但仍留在列表里,用 `clear` 结束。
